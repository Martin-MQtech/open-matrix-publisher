# 产品与视觉设计方案（Open Matrix Publisher）

> **本文档性质**：本文件是 Open Matrix Publisher 在**产品形态、视觉设计、账号/数据架构、分阶段路线图**上的唯一权威方案，由 2026-08-18 的"Pro 规划"形成。后续任何接手者（人类或 AI Agent）在动手写代码前，必须先对照本文件；`执行手册.md` 中与本文件冲突的旧描述，以本文件为准，并按本文档路线逐步清理。
>
> **一句话结论**：
> - **Slogan（2026-08-18 定稿）= 一条内容，多域分发**：定位锚点是「一条内容」（不限视频/图文/文章）与「多域分发」（跨平台/跨渠道/跨地域，不限平台数量）。**禁止用具体平台数量（如"20 平台"）作品牌口号**，平台数只作为事实数据出现在矩阵表中。
> - 产品形态 = **Web 优先**（唯一交付物），桌面 DMG 只是同一 Web UI 的套壳，属于后期封装。
> - 视觉 = **黑 / 灰 + 橙黄**三色，扁平、线条、几何，彻底去赛博朋克（去渐变、去光晕、去霓虹）。
> - 平台图标 = 使用各平台**官方扁平单色 logo**（Simple Icons 类），不再用 FontAwesome 彩色小方块。
> - 账号 = **暂不做注册/登录，整体后置**；产品形态为开源、可下载到各地、本地运行、免注册。
> - 节奏 = **先收尾 Phase 1（视频分发），再做 Phase 2（文章/图文）**；账号/CRM 后置。

## 0. 复用优先原则（Reuse-First，第一执行原则）

> 开源社区已经解决了大量通用问题，本项目的竞争力来自**整合与调度**，而非重造轮子。任何新模块立项前，必须先走下面的判断流程。

**决策规则**：
1. 先问“开源社区是否已有成熟实现？”——有则优先复用/封装，除非复用成本明显高于自研（许可证冲突、可维护性差、过度臃肿）。
2. 复用方式优先级：直接调用成熟库/CLI ＞ 封装上游项目 ＞ 引入 SaaS/BaaS ＞ 最后才自研。
3. 每个 Phase 启动前，先在计划里列出“本阶段复用清单”，未调研清楚不得动工。

**已确认复用（当前已用或已定）**：
| 模块 | 复用来源 | 状态 |
|---|---|---|
| 国内平台视频上传（抖音/快手/小红书/B站/视频号/YouTube） | social-auto-upload (SAU) | 已用 |
| 反检测浏览器自动化 | Patchright（Playwright fork） | 已用 |
| **Instagram Reels 移动端 API** | **instagrapi（4.2k+ stars 开源库）** | **已用，2026-08-18 实测发布成功**（绕过 Web 反自动化） |
| 平台品牌图标 | Simple Icons | 已定，Phase 1 接入 |
| 字体 | Google Fonts（Fraunces / Inter / Noto Sans/Serif SC） | 已用 |
| 通用 UI 图标 | Font Awesome | 已用（品牌图标改走 Simple Icons） |
| 桌面封装 | pywebview / Tauri | 已定方向，Phase 3 落地 |

**已验证的开源方案（2026-08-18 调研）**：
| 平台/需求 | 方案 | 结论 |
|---|---|---|
| LinkedIn 发布（含视频） | **Postiz**（gitroomhq/postiz-app，开源自托管，30+ 平台） | 走 **LinkedIn 官方 Marketing API**（OAuth 授权），非浏览器自动化——这是"别人已解决"的成熟路径，**本项目暂不自行硬磕 LinkedIn Web 反自动化，待官方 API 通道**（Postiz 或直接接 LinkedIn API） |

## 1. 产品定位与产品形态

### 1.1 双身份定位
1. **内部工具**：先服务木齐科技（MUQI Tech）内部，满足"营销素材（视频/图文/文章）多平台分发"的日常刚需，用公司色系。
2. **对外开源产品**：面向有同样"跨境/出海/多平台内容分发"需求的企业与创作者，通过开源（MIT）积累影响力和真实用户。

### 1.2 产品形态（强制）
- **Web 是唯一核心交付物**：一个清晰的单页工具 + 本地后端（Flask 桥接服务），覆盖绝大多数使用场景。
- **桌面 App 是后续封装**：待 Web 成熟后，用 pywebview/Tauri 把同一套 Web UI 打成 **macOS DMG**（Windows/Linux 后置）。桌面封装**不改变**产品逻辑，只解决"双击即用"和图标/窗口外壳。
- **AI-Native 是差异化**：保留 CLI / MCP / REST 接口，让任何 AI Agent 都能接管分发；但对外展示页保持极简。

### 1.3 平台网络动态生长（强制理念，2026-08-18 定稿）
- 当前 20 平台是**起点**，不是终点：按"选择更好的渠道"持续增删调优，平台会不断增加、调整、也可能下线。
- **平台清单是数据，不是身份**：前端 `PLATFORMS` 数组是唯一用户侧数据源，后端引擎清单 / `interactive_login` / `mcp_server` 同步维护，审计 B4 强制一致性；UI 计数（国内/海外/已登录）全部动态计算，禁止硬编码数量。
- **品牌与 Slogan 不得绑定具体平台数**（Slogan 定稿：一条内容，多域分发）；平台数量只出现在矩阵表的"当前已接入"事实列。

### 1.4 双模式使用（产品理念，2026-08-18 定稿）

> 传统软件无法被 AI Agent 直接操纵；而本项目所有后端接口（REST / CLI / MCP）在开发之初就是由 AI Agent 驱动打磨出来的。因此产品天然支持**两种使用方式**，且第二方式可能更流行：

**模式 A —— 独立软件使用（人类直接操作）**
- 打开控制台 → 选内容 → 填文案 → 勾平台 → 一键发布；数据与 Cookie 留在本机。
- 适合日常手动操作、演示、非技术用户。

**模式 B —— AI Agent 接管（后台全自动）**
- 用户把**项目文件夹 / 工具箱**交给 AI Agent（如 Claude / Antigravity / Freebuff），直接下指令：
  "把 `素材/` 里新视频分发到抖音、TikTok、X、Facebook"——Agent 在后台全部跑完、全部发送、全部自动完成。
- 依赖：稳定的 REST 接口（`/api/*`）+ CLI 入口（`dispatch.py` / MCP server）+ 本地 Cookie 库（`cookies/`），三者必须持续保持可用、可被脚本调用。
- **架构要求（强制）**：任何 UI 改动不得破坏接口层；新增平台必须同步暴露到 `real_uploader_engine` + `interactive_login` + MCP 平台清单，确保 Agent 也能驱动。

**两种模式共享同一套后端与登录态**——软件界面只是模式 A 的壳，模式 B 直接复用全部引擎能力。

### 1.5 平台接入策略：能复用就不硬磕（2026-08-18 定稿）
- 平台反自动化（Web 发布流程拦截）是常见障碍，**不投入无限时间硬磕**：
  1. 优先找开源成熟方案（instagrapi 类移动 API 库、Postiz 类调度器、官方 API）；
  2. 别人已解决的（如 LinkedIn 走官方 Marketing API），直接采用或等其成熟后接入；
  3. 暂时无法解决的平台，**降级为"暂不支持"**（前端置灰标记），不阻塞主线交付。
- 当前状态：X / Facebook / TikTok / Instagram 已实测发布成功；LinkedIn 标记"暂不支持（待官方 API）"。

### 1.6 核心使用流程（唯一主流程）
```
① 选择内容（本地文件 / 远程直链） → ② 填写文案（标题/描述/标签） → ③ 勾选平台 → ④ 发布 → 进度/取消 → 分发记录（防重可见）
```
后续第二阶段在此主流程上叠加"内容类型：视频 / 图文 / 文章"。

## 2. 视觉设计系统（Design System）

### 2.1 色彩（强制，黑/灰平衡 + 橙黄主色）
| Token | 值 | 用途 |
|---|---|---|
| `--bg` | `#15130f` | 暖黑页面底 |
| `--surface` | `#1c1a15` | 炭黑卡片 |
| `--surface-2` | `#23201a` | 灰色次级面板/输入框 |
| `--ink` | `#f2eee6` | 主文字（暖白） |
| `--muted` | `#9a9384` | 次要文字（灰） |
| `--faint` | `#6f695c` | 弱化文字/占位 |
| `--line` | `rgba(242,238,230,.08)` | 发丝边框 |
| `--line-2` | `rgba(242,238,230,.16)` | 强调边框 |
| `--accent` | `#e8892e` | 主色（橙） |
| `--accent-2` | `#f3b25a` | 辅色（黄） |
| `--accent-grad` | `135deg #f5b25a → #e8892e → #d6762a` | 仅用于主 CTA |
| `--success` | `#9cc08f` | 成功/已登录（低饱和绿） |
| `--danger` | `#d07b6c` | 失败/取消（低饱和红） |

### 2.2 字体
- 标题/大数字：`Fraunces` + `Noto Serif SC`（衬线，人文编辑感）。
- 正文/控件：`Inter` + `Noto Sans SC`。
- 数字/代码：系统等宽。

### 2.3 质感规范（强制，去花哨）
- 边框一律**发丝级**；阴影一律**中性、低对比**（无彩色光晕）。
- **渐变只允许出现在主 CTA 按钮一处**；其余一律纯色。
- 禁止：径向背景、霓虹描边、`backdrop-filter` 大面积玻璃、`box-shadow` 带色光晕。
- 圆角：卡片 12–14px、按钮 9–10px、小徽标 4–8px，保持克制。

### 2.4 Logo 品牌规范（强制，2026-08-18 定稿）

**图形语义**：大 M 作背景（Matrix / MUQI 首字母，暖白粗体几何）+ 中心一枚橙黄渐变 O（Open）+ 最外一圈细环收住框架——"Open Matrix"，即"开放的全域矩阵"。炭黑圆角底。**核心设计点：O 的圆洞把 M 中间的 V 形双臂套出，V 完整清晰可见（M 就是 M）**；O 加大（r12）以增强 M 与 O 相交处的 V 形可视化。**渐变仅限 O 一处**（橙黄渐变 `#ffc36e→#f68f2e→#d96f1f`），M 与外圈保持纯色，无光晕。

**资产清单**：
| 文件 | 用途 |
|---|---|
| `logo.svg` / `logo.png`（1024px） | **标准版**（炭黑圆角底），网页顶栏 / README / 桌面 |
| `logo-mono-white.svg` / `.png` | 单色暖白 `#f2eee6`，透明底，深色表面 |
| `logo-mono-black.svg` / `.png` | 单色墨黑 `#15130f`，透明底，浅色表面 / 打印 |
| `logo-mono-orange.svg` / `.png` | 单色橙 `#e8892e`，透明底，强调场景 |
| `favicon.ico` | 16/32/48/64/128/256 多尺寸，浏览器 |
| `icon.icns` / `icon.ico` | macOS / Windows 打包图标 |

**① 深底用法（主场景）**
- 站点/App 深色 UI（`--bg #15130f`）上：用**标准版**（炭黑圆角底自带对比，直接放置）或**单色暖白版**（透明底，用于深色表面水印/物料）。
- 深底上禁用暖白以外的浅色混搭；橙黄渐变 O 是唯一强调色。

**② 浅底用法**
- 文档/README 白底、浅灰底：用**标准版**（炭黑圆角底对比充足）或**单色墨黑版**（透明底，打印/单色印刷）。
- 浅底上**禁用**单色暖白版（无对比）。

**③ 单色规则**
- 暖白 `#f2eee6`：仅限深色背景（保证对比度）。
- 墨黑 `#15130f`：浅色背景、打印、灰阶媒体。
- 橙 `#e8892e`：仅限强调场景（印章、水印、小尺寸 CTA、活动标记），**不作大面积填充**。
- 单色版 M / O / 外圈必须同色，三色互不混用。

**④ 最小尺寸**
- 数字端：**16px 绝对下限**（favicon 场景）；UI/网页 ≥ **24px**；推荐 ≥ 32px（顶栏现用 32px）。
- 桌面图标：系统按 16/32/64/128/256 自动取用（ico/icns 已内置各档）。
- 印刷/实体：最小 **10mm**（≈0.4in）高；低于此尺寸改用单色版。

**⑤ 留白（安全区）**
- 四周留白 ≥ **logo 高度的 25%**；小尺寸场景（≤32px）最小留白 8px。
- 禁止文字、控件、边框侵入安全区。

**⑥ 禁用清单（Don'ts）**
- 不变形：禁止拉伸、压扁、倾斜（保持 1:1 与圆角比例）。
- 不旋转、不裁切、不加外底色块（除非用标准版自带圆角底）。
- 不换色：除标准版与三个单色版外不得自创配色。**渐变仅限标准版 O 一处**（橙黄渐变）；禁止渐变 M、渐变外圈、光晕、描边、投影。
- 不放在有图案/照片/低对比背景上；优先纯色背景。
- **不使用旧版"放射 8 节点"构图（已废弃）**。

### 2.5 平台图标规范（强制）
- **弃用 FontAwesome 品牌图标**（近似图标 + 彩色小方块 + 渐变光晕，观感廉价且不准确）。
- 改用 **Simple Icons（simpleicons.org，约 3453 个平面单色品牌 SVG）**：
  - CDN 形式：`https://cdn.simpleicons.org/{slug}/{brandHex}`；**推荐下载 SVG 本地自托管**，保证桌面/离线可用。
  - 渲染：**18px、单色、官方品牌色、中性灰底卡片上直接放置**，不再套彩色底框；深色品牌色（TikTok 黑、X 黑、抖音黑等）在深色底上反白。
- 覆盖不到的国内平台（视频号/百家号/好看视频等）用**统一规格的扁平单色字标/首字徽标**替代，保持同一视觉语言。
- 目标效果：平台卡片 = "平面 logo + 平台名 + 状态/取消"，干净、一眼可辨。

## 3. 信息架构（页面结构，极简）

单页、自上而下，学习成本趋近于零：

1. **顶栏**：Logo + 产品名 + 引擎连接状态 + GitHub/官网两个安静链接。
2. **四步主流程**（左列：①选择内容 → ②文案；右列：③选择平台 → ④发布）。
3. **分发记录**：历史发布（成功/防重）+ 进行中任务（可取消）。
4. **底部**：极简备案式页脚（开源协议 + 公司 + 隐私承诺）。

明确的"不做"清单：首页不放营销 Hero、不放 20 平台展示墙、不放技术支柱卡、不放 MCP 配置代码块——这些回归 README/docs 或独立开发者页。

## 4. 账号体系与 CRM（已后置 · 远期参考）

> **决策（2026-08-18 更新）**：暂不做用户注册/登录。产品形态为**开源、可下载到各地、本地运行、免注册**。本章仅作远期（将来若做托管版/团队版）参考，不列入近期排期。

### 4.1 结论（已更新）
**暂不做注册/登录，整体后置。** 当下产品就是"开源下载、本地运行、免注册可用"；注册/云同步/CRM 留到远期，不在 Phase 1/2 排期。

### 4.2 为什么不做硬门槛
- 开源工具的传播靠"零摩擦上手"（PLG + GitHub Stars），第一屏就要能干活。
- 硬性注册会显著流失用户，与 `执行手册.md` 的开源增长战略冲突。
- 但"留联系方式、形成个人数据库、沉淀线索"是真实且正当的商业诉求，应通过**自然节点收集 + 云同步增值**实现，而不是用门槛吓跑人。

### 4.3 收集字段（最小集，可跳过）
- 姓名 / 邮箱（用于联系与找回）
- 手机（可选，用于国内线索触达）
- 公司 / 团队（可选）
- 业务类型（可选：外贸 B2B / 跨境电商 / 内容创作者 / 品牌方 / 其他）
- 用途告知 + 同意（合规必需）

### 4.4 数据库复杂度：三档对比（决策用）
| 方案 | 复杂度 | 工期（MVP） | 说明 |
|---|---|---|---|
| A. 纯本地 JSON/SQLite | 低 | 0.5–1 天 | 无云、无登录；记录与线索仅存本机，线索靠"导出/主动提交" |
| B. 自托管 BaaS（Supabase / Appwrite） | 中 | 1–3 天 | 自带 auth + Postgres + 管理后台，安全成本低，推荐 |
| C. 全自研后端 + auth + 部署运维 | 高 | 1–2 周+ | 安全/合规/运维自担，不推荐起步就用 |

**推荐 B**：先用 BaaS 验证"注册 → 登录 → 记录同步 → 线索后台"闭环，量起来后再考虑自研或换更重方案。

### 4.5 数据模型草案
```
users            (id, email, phone, company, business_type, created_at, last_login_at)
dispatch_records (id, user_id, content_name, title, platform, status, published_at, synced_at)
leads            (id, user_id?, name, email, phone, company, business_type, source, consent, created_at)
sync_log         (id, user_id, direction, status, detail, created_at)
```
本地仍保留 `dispatch_history.json` 作为离线事实源；云同步只是增量镜像。

### 4.6 隐私与合规（强制）
- 收集前明确告知用途并取得同意；支持导出与删除（PIPL / GDPR 底线）。
- **Cookie / 视频文件 / 账号凭证仍然 100% 本地**，绝不默认上传云端；仅"记录元数据 + 用户资料"可云同步。
- 不存储明文密码（BaaS 自带）；不留存平台 Cookie 副本到云。

---

### 4.7 澄清：网页人人可用 ≠ 分发集中在服务器（强制理解）
“所有人都能用网页分发”是通过 **开源 + 本地运行**实现的，而不是一台大服务器替所有人发视频。
- 分发引擎（浏览器自动化 + 平台登录 + 上传）**必须运行在每个用户自己的机器**，原因：
  1. 平台 Cookie/登录态是个人私有凭证，不能集中到服务器（否则=服务商替所有人持有账号）；
  2. 集中上传违背“Cookie 不离本机”的隐私卖点，并有合规风险（PIPL/GDPR）；
  3. 平台会识别机房 IP 与自动化特征，集中上传极易被批量封号。
- 云端只负责**轻量元数据**（注册/登录、记录同步、线索收集；本项也已后置）。
- 若未来做“零安装”的托管版（SaaS），只能走“**每个用户一个隔离浏览器容器**”的高成本模式，属于远期选项，不是首期目标。

### 4.8 容量、排队与人数上限（何时才需要）
- “排队/限流/人数上限”只作用于云端轻量层；该层极轻，首期无需排队（本项已随注册后置）。
- 真正的资源瓶颈在每个用户自己机器的并发浏览器数，已用本地信号量 `OMP_MAX_CONCURRENT` 控制（本地级限流）。
- 何时才需要排队：未来若做托管版（服务端跑浏览器），才需要“容器池 + 队列（如 Redis）”，届时同样**复用现成方案，不自研**。

## 5. 本地 vs 云端职责边界（不可动摇）

| 职责 | 归属 |
|---|---|
| 浏览器自动化、扫码登录、Cookie、上传执行 | **本地引擎**（隐私卖点） |
| 文案、标签、防重历史（离线可用） | **本地**（JSON 事实源） |
| 用户注册/登录、记录云备份、团队协作、线索后台 | **云端**（可选，Phase 2） |
| 平台凭证/密码 | **永不落云** |
